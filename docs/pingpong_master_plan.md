当前阶段的正确定位应是：

> `model_49.pt` 只是一个单臂基础击球技能和物理事件验证器，不是未来双臂自博弈的策略基础。

原因很明确：

- 当前场景只有一个 `robot` 实体；
- 动作只有 6 维；
- 策略围绕一条固定横拍轨迹做小残差；
- 触拍后动作被清零；
- 发球无旋转、速度范围窄；
- 一个 episode 只包含一次回球；
- reward 主要评价“这一次球是否回过去”，没有连续对局状态。

直接在这个基础上继续 PPO，只会把“固定轨迹回球”做得更稳定，无法自然发展出双臂对拉、落点选择、速度变化、旋转变化、连续调整和对手适应。

我建议把长期系统拆成四层。

**第一层：基础击球技能**

保留当前参考轨迹，但目标不再只是成功率，而是建立可复用的击球技能库：

- 不同来球横向位置；
- 不同速度和高度；
- 不同击球点；
- 不同拍面角度；
- 不同出球方向；
- 不同挥拍速度；
- 不同随挥形式。

这里可以继续使用 residual policy，但必须逐渐扩大动作范围。当前 ±0.015 rad、时钟最多 1.02 倍的限制，只适合稳定化，不能支撑技能扩展。

**第二层：单臂连续回球**

把“一次发球、一次回球、结束”改成连续状态机：

```text
发球
→ 对手侧落台
→ 本侧落台
→ 准备
→ 击球
→ 对手侧落台
→ 对手再次击球
→ ...
```

这一层需要先解决：

- 多次触球；
- 每次击球后的球权转换；
- 机器人接触和球拍接触优先级；
- 连续回合中的 timeout；
- 球出界和桌面二次落地；
- 每一拍的 hit / return / landing / quality 记录。

如果事件判定仍然存在 `below_net` 误判，成千上万次自博弈会把错误标签放大，训练结果会越来越不可信。

**第三层：双臂固定对手训练**

不要一开始就让两个策略同时自由学习。更稳的顺序是：

1. 左臂固定；
2. 右臂学习；
3. 右臂固定；
4. 左臂学习；
5. 两边交替更新；
6. 最后才进行同时更新。

否则两个 PPO 同时变化时，环境对每个策略都是非平稳的：一个策略刚学会击球，对手马上改变，价值函数会不断失效，训练日志看起来可能在改善，但实际策略会退化。

这一步需要引入：

- 两个独立策略或共享策略；
- `active_arm_side`；
- 每个机械臂独立的观测和动作；
- 共享球状态；
- 双方击球事件；
- 回合级奖励；
- 每一拍的局部奖励。

**第四层：自博弈和能力进化**

当双臂可以稳定完成连续对拉后，才适合做成千上万次对局。此时应使用：

- opponent pool，而不是只保留当前最新策略；
- 历史 checkpoint 随机采样；
- 冻结对手评估；
- Elo 或胜率矩阵；
- 防止策略只学会针对当前对手；
- 不同技能策略的混合，例如防守、快速、斜线、追身、短球。

否则两个策略可能共同退化成一种很容易互相配合的简单球路，并不代表能力提高。

奖励也需要分层。只用最终胜负会太稀疏，只用预测落点又会产生投机行为。建议把奖励拆成：

```text
击球有效性
+ 回球合法性
+ 对方半台落点质量
+ 出球速度
+ 过网高度
+ 球路变化
+ 连续对拉长度
+ 对手造成的困难程度
- 机械臂碰撞
- 出界
- 重复击球
- 过大动作
```

其中“胜负”应该是最高层奖励，而不是唯一奖励。

PACE 的内容适合放在第二层和第三层：

- 学习型击球点预测器：帮助机器人提前移动；
- 物理预测回球奖励：评价击球瞬间的落点和过网高度；
- 特权 Critic：帮助训练价值函数；
- 观测噪声和物理随机化：提高泛化。

但 PACE 不能替代双臂任务本身的状态机和动作空间设计。它解决的是“如何更有效地学习复杂击球”，不是“如何把单次回球环境变成连续双臂对局”。

我会把当前项目的路线定成：

```text
单臂固定回球
→ 单臂多来球泛化
→ 单臂多技能击球
→ 单臂连续对拉
→ 双臂轮流训练
→ 双臂自博弈
→ 对手池和长期联赛
```
